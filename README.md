## 1. Project overview

This project analyses 5,574 SMS messages labelled **ham** (legitimate) or **spam**. The whole workflow runs in **JupyterLab inside a custom Docker container**:

```
Dockerfile → custom image → container → JupyterLab → data cleaning → sampling → text analysis
→ TF-IDF → classification (Naive Bayes + Logistic Regression) + K-Means → persistent outputs (bind mount) → Docker Hub
```

The notebook `notebook/analysis.ipynb` covers:

* **Dataset understanding:** `head`, `shape`, `columns`, `dtypes`, `info`, descriptive statistics, and the role of each column.
* **Cleaning:** missing values, invalid labels, and 403 duplicate rows. The shape is shown before and after cleaning.
* **Selection:** `loc` conditional selection, and `iloc` positional selection including `np.r_`.
* **Transformations:** type conversion, label encoding, feature creation, binning, normalization and category consolidation.
* **Sampling:** simple random, stratified and cluster sampling, plus a 300-repetition precision experiment.
* **Correlation:** a heatmap of 7 numerical text features plus the label.
* **Text cleaning:** a new `cleaned_text` column; the original text is kept unchanged. URLs, numbers and currency are replaced with placeholder tokens.
* **Text statistics:** tokenization, the top-20 words with and without stop words, a spam vs ham comparison, and 6 written insights.
* **Classification:** TF-IDF + **Multinomial Naive Bayes** and **Logistic Regression** in leakage-free `Pipeline`s, with 5-fold CV, test metrics and confusion matrices.
* **Clustering:** **K-Means** on TF-IDF → TruncatedSVD (LSA). k is chosen by a silhouette/elbow experiment, and the clusters are interpreted and compared with the labels.

### Key results (generated by the notebook, see `output/`)

| Model (test set, spam = positive) | Accuracy | Precision | Recall | F1 |
|---|---|---|---|---|
| Multinomial Naive Bayes | 0.9884 | 0.9685 | 0.9389 | 0.9535 |
| Logistic Regression | **0.9932** | **0.9844** | **0.9618** | **0.9730** |

**K-Means** chose **k = 9** (silhouette 0.0605, the maximum over k = 2…10). One cluster contains 567 of the 653 spam messages (86.8%), and the other eight clusters are ≥ 97% ham conversation topics. Purity is 0.938 against a 0.874 majority-class baseline.

## 5. Dockerfile explanation

```dockerfile
FROM quay.io/jupyter/scipy-notebook:latest                     # (1) base image
LABEL ...                                                       # metadata
ENV PROJECT_DIR=/home/jovyan/bd-a1                              # (2) project folder path
COPY --chown=${NB_UID}:${NB_GID} requirements.txt /tmp/requirements.txt
RUN pip install --no-cache-dir -r /tmp/requirements.txt && rm /tmp/requirements.txt   # (3)
RUN mkdir -p ${PROJECT_DIR}/data ${PROJECT_DIR}/notebook ${PROJECT_DIR}/output/figures # (4)
COPY --chown=${NB_UID}:${NB_GID} data/dataset.csv ${PROJECT_DIR}/data/dataset.csv              # (5)
COPY --chown=${NB_UID}:${NB_GID} notebook/analysis.ipynb ${PROJECT_DIR}/notebook/analysis.ipynb
WORKDIR ${PROJECT_DIR}                                          # (6)
EXPOSE 8888                                                     # (7)
CMD ["start-notebook.py", "--ServerApp.root_dir=/home/jovyan/bd-a1", "--ServerApp.ip=0.0.0.0", "--ServerApp.port=8888"]  # (8)
```

1. **Base image.** This is the official Jupyter Docker Stacks *scipy* image. It provides JupyterLab and the scientific Python stack and runs as the non-root user `jovyan` (UID 1000).
2. **Project folder.** `/home/jovyan/bd-a1` is the project folder inside the image.
3. **Dependencies.** They are installed from `requirements.txt`. The file is copied **before** the data and notebook, so this slow layer stays cached when only the notebook changes. `--no-cache-dir` keeps the layer small.
4. **Folder structure.** `data/`, `notebook/` and `output/figures/` are created inside the image.
5. **Copy files.** The dataset and the notebook, both prepared on the host, are copied into the image. `--chown` makes `jovyan` the owner so JupyterLab can save the notebook.
6. **WORKDIR.** This sets the project folder as the working directory, so commands and JupyterLab start there.
7. **EXPOSE 8888.** This documents that JupyterLab listens on port 8888. It does not publish the port; `-p` does that.
8. **CMD.** It starts JupyterLab with the base image's start script. The access URL and token are printed to the container logs.

### Docker image layers

An image is a stack of **read-only layers**. Each filesystem-changing instruction (`FROM` layers, `COPY`, `RUN`) adds one layer, and `ENV`, `WORKDIR`, `EXPOSE`, `LABEL` and `CMD` only change metadata.
* Layers are **content-addressed and cached**. When you rebuild, Docker reuses every layer up to the first instruction whose input changed. That is why `requirements.txt` is copied and installed *before* the notebook is copied: editing the notebook only rebuilds the last small layers.
* Layers are **shared**. Several images built on `scipy-notebook` store the base layers only once, and `docker push`/`pull` transfer only the layers the registry or host does not already have.
* A **running container** adds a thin **writable layer** on top of the read-only image layers (copy-on-write). Anything written there disappears when the container is removed, which is why results are written to the bind-mounted `output/` folder.
* Inspect the layers with `docker history bd-a1:latest`.

## 6. Image vs container, and port mapping

* An **image** (`bd-a1:latest`) is a read-only template: a filesystem snapshot plus metadata, built from the Dockerfile. It does not run.
* A **container** (`bd-a1-container`) is a **running (or stopped) instance** of an image. It has its own process, network interface and writable layer. Many containers can be started from one image.
* `-p 8888:8888` means **`HOST_PORT:CONTAINER_PORT`**:
  * the **left** number is the port on **your computer (host)**, which you open in the browser (`http://localhost:8888`);
  * the **right** number is the port **inside the container**, where JupyterLab listens.
  * If port 8888 is already used on your machine, change only the host side, for example `-p 8889:8888`, and open `http://localhost:8889`.

```powershell

```

### Windows Command Prompt (cmd.exe)

```bat
docker run -d --name bd-a1-container -p 8888:8888 -v "%cd%\output:/home/jovyan/bd-a1/output" bd-a1:latest
```

**Optional: also persist notebook edits.** Add a second bind mount for the notebook folder: `-v "$(pwd)/notebook:/home/jovyan/bd-a1/notebook"`. The executed notebook, with all its outputs, is then saved back to the host.

**Linux only: file permissions.** Inside the container, files are written by user `jovyan` (UID 1000). If your host user has a different UID and the container cannot write to `output/`, either make the folder writable or let the container adopt your UID:

```bash
docker run -d --name bd-a1-container -p 8888:8888 --user root -e NB_UID=$(id -u) -e NB_GID=$(id -g) -v "$(pwd)/output:/home/jovyan/bd-a1/output" bd-a1:latest
```

Docker Desktop on Windows/macOS handles this automatically.

### Bind mount explanation

`-v <host_path>:<container_path>` is a **bind mount**. The host folder `bd-a1/output` and the container folder `/home/jovyan/bd-a1/output` become **the same directory**. Everything the notebook writes to `output/` (CSV, TXT, figures) appears immediately on the host and **remains after the container is stopped or removed**. Without the mount, the files would live only in the container's writable layer and would be lost on `docker rm`.

*Bind mount vs volume:* a **bind mount** maps a specific host path that you choose and can browse directly, which is ideal for deliverables. A **named volume** (`-v mydata:/path`) is managed by Docker under Docker's own storage area. It is portable and good for databases, but it is not a normal project folder on your disk.

## 11. Docker lifecycle commands

| Command | Purpose |
|---|---|
| `docker build -t bd-a1:latest .` | Build the image from the Dockerfile |
| `docker images` | List local images; shows that `bd-a1` exists, with its tag, ID and size |
| `docker history bd-a1:latest` | Show the image layers |
| `docker run -d --name bd-a1-container -p 8888:8888 -v ...` | Create **and** start a container |
| `docker ps` | List **running** containers (status, ports `0.0.0.0:8888->8888/tcp`) |
| `docker ps -a` | List **all** containers, including stopped/exited ones |
| `docker logs bd-a1-container` | Show the container's output (JupyterLab URL and token) |
| `docker inspect bd-a1-container` | Full JSON configuration: mounts, port bindings, state, image ID, env |
| `docker stop bd-a1-container` | Stop the container gracefully (state → *Exited*) |
| `docker start bd-a1-container` | Start the stopped container again (same writable layer) |
| `docker rm bd-a1-container` | Remove the stopped container (the bind-mounted outputs stay on the host) |
| `docker rmi bd-a1:latest` | Remove the image (after removing its containers) |

Useful `docker inspect` filters:

```bash
docker inspect --format "{{json .Mounts}}" bd-a1-container
```

```bash
docker inspect --format "{{json .NetworkSettings.Ports}}" bd-a1-container
```

```bash
docker inspect --format "{{.State.Status}}" bd-a1-container
```

### Container lifecycle

```
             docker build            docker run (= create + start)
Dockerfile ───────────────► IMAGE ───────────────────────────► RUNNING container
                                                               │      ▲
                                                   docker stop │      │ docker start
                                                               ▼      │
                                                           STOPPED (Exited) ──docker rm──► removed
                                                    (docker pause/unpause → PAUSED; docker kill → immediate stop)
```

1. **Created:** `docker create` or the first half of `docker run` builds the container's writable layer and configuration.
2. **Running:** the main process (JupyterLab) runs. `docker ps` shows it, and `docker logs` shows its output.
3. **Paused** (optional): processes are frozen with `docker pause` and resumed with `docker unpause`.
4. **Stopped / Exited:** after `docker stop`, a crash, or the main process ending. The container is still listed by `docker ps -a`, and its writable layer still exists.
5. **Removed:** `docker rm` deletes the container and its writable layer. The **image** and **bind-mounted files** are not affected.

## 14. Reproducibility

* **Deterministic:** a single seed (`RANDOM_STATE = 42`) is used for sampling, the train/test split, cross-validation, TruncatedSVD and K-Means.
* **Self-contained:** the dataset and notebook are copied into the image, and no downloads happen at run time.
* **Regenerated outputs:** every file in `output/` is regenerated by *Restart Kernel and Run All*, and the last cell asserts that all required outputs exist.
* **Portable paths:** the notebook resolves the project root automatically. It works when started from `notebook/` (JupyterLab) or from the project root (`nbconvert`).
* **Pinned base:** `:latest` is used because the assignment requires it. For long-term reproducibility, push your built image with a fixed tag (`v1`) and share that tag. Teammates then get exactly the same layers.
